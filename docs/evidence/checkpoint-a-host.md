# Checkpoint A: UIKit render host (FF-02, FF-03)

Date: 2026-11-08 · Tasks: FF-02, FF-03 · Branch: `implement/milestone-1`

This record covers the diagnostic-triangle renderer, its UIKit `MTKView` host,
and the host's lifecycle schedule. It contains Mac GPU unit tests and iOS
Simulator runs only. **No physical iPhone or iPad was used**, so it establishes
no device rendering, GPU timing, energy, or performance result.

## What exists

- `TriangleRenderer` draws through a conventional `MTLCommandQueue` with at
  most two frames in flight. `FrameSlots` hands out a per-frame uniform buffer
  only after the GPU completed that slot's previous frame and returns `nil`
  instead of waiting. The renderer asks the host for a drawable only after it
  holds a free slot.
- Construction failures throw `RendererError`; the lab shows the error text in
  place of the render view.
- `Triangle.metal` compiles into `default.metallib` in the package resource
  bundle; the renderer loads it with `makeDefaultLibrary(bundle: .module)`.
- `RenderSchedule` (core, no UIKit) decides pacing from mode (requested or
  continuous), scene activity, visibility, and drawable size; it defers a
  requested frame that found no slot or drawable until a frame completes; its
  animation clock advances only while drawing continuously, by at most 0.1 s
  per frame.
- The lab's `SceneRenderView` (`MTKView`, `autoResizeDrawable = false`) reports
  its bounds and `traitCollection.displayScale` from `layoutSubviews`; the
  schedule turns them into the drawable size. Each window scene has its own
  controller, renderer, schedule, and view. Its scene delegate forwards that
  scene's lifecycle callbacks.

### Two scenes (iPad Air 11-inch (M4) simulator, manual)

Driven through an Xcode MCP device-interaction session in iPadOS windowed
multitasking. Two windows of the lab were open and both scenes were active.

1. Window A was resized by its resize grabber to 407.5 × 648.5 pt. Its drawable
   followed to 815 × 1297 px at 2.0, and it submitted 21 requested frames during
   the live resize and none afterwards.
2. Window B ran in continuous mode at 750 × 972 px the whole time; its counter
   rose from 591 to 3152 frames while A stayed still and was resized.
3. Hiding B stopped it at 5455 frames for more than 3 s (pacing `stopped`); A

## Drawable acquisition on the main thread

`MTKView.currentDrawable` calls `CAMetalLayer.nextDrawable()` synchronously on
the main thread. The lab measures the time spent there:

| Run | Longest wait observed |
| --- | --- |
| Full UI suite, first run (one maximum for the whole launch) | 2.9 ms before Home; 67 ms after returning from the background in continuous mode |
| Background, hidden, and requested-background tests, second run (split by scene activity) | 4.1 ms while active; 12.1 ms while not active |
| Full UI suite, final run (split by scene activity) | 2.2 ms while active; 5.3 ms while not active |

Frostfield itself never waits for a frame slot. These waits occur inside
Core Animation's drawable acquisition. The cause (first-use allocation after
launch, resize, or resume, or every drawable still queued for display) is not
isolated, and simulator timings are not device evidence. FF-03's bounded
in-flight criterion therefore stays open until a physical-device run measures
this. If the waits persist on a device, the next step is to defer the redraw
owed on return from the background until the scene is active, or to acquire
drawables off the main thread through a `CAMetalLayer` host.
