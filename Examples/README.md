# Frostfield examples

Open `Frostfield.xcworkspace`. It contains the Frostfield package and the
`FrostfieldLab` iOS/iPadOS app, which depends on the package through a local
package reference (`../..`). No signing team is configured; run the lab on an
iOS Simulator or add your own team locally without committing it.

| Scheme | Destination | What it runs |
| --- | --- | --- |
| `Frostfield` | My Mac | Package unit tests, including off-screen GPU renders with readback. The scheme's test action sets `MTL_DEBUG_LAYER=1` for Metal API validation and `FROSTFIELD_REQUIRE_API_VALIDATION=1`, which makes `API validation wraps the device when requested` fail rather than skip if validation is missing. |
| `FrostfieldLab` | An iOS Simulator | The lab app and its XCTest UI tests. |
| `Metal4ComparisonTests` | My Mac (or an iOS Simulator) | FF-04 experiment: conventional versus Metal 4 output and lifetime tests, with Metal API validation. On a simulator the Metal 4 code is compiled out. |
| `Metal4Benchmark` | My Mac | FF-04 experiment: Release timing tool, API validation off. |

Xcode also lists the package's autogenerated scheme under the same name
(`Frostfield (Frostfield)`). It sets neither variable, so its GPU tests run without
Metal API validation and the validation check is skipped; choose the workspace's
shared scheme, `Frostfield (Frostfield Workspace)`. CI does not depend on which of the
two `xcodebuild` resolves: it passes both variables to the test runner itself
(`TEST_RUNNER_MTL_DEBUG_LAYER=1`, `TEST_RUNNER_FROSTFIELD_REQUIRE_API_VALIDATION=1`).

## FrostfieldLab

The lab is the UIKit `MTKView` fixture for the rendering host. Each window scene
creates its own `SceneViewController`, `TriangleRenderer`, and view; nothing is a
process-wide singleton. It draws the package's diagnostic triangle (red apex,
green lower left, blue lower right) from the shader library packaged in the
Frostfield resource bundle.

A `RenderSchedule` paces each scene's view. The panel at the bottom switches
between requested drawing (a still scene draws only after an invalidation such as
a resize or the Redraw button) and continuous drawing, hides and shows the render
view, and, where the system supports multiple windows, opens another window. The
status text shows the scene's mode, activity, pacing, drawable size and display
scale, the renderer's submitted, completed, and skipped frames, and the host's
draw-callback counters, including callbacks and frames while the scene was not
active. VoiceOver reads that visible text. Only when the app is launched with
`-FrostfieldLabUITesting`, as the UI tests do, does the label also carry the
counters as `key=value` pairs in its accessibility value.

The fixture switch at the top of the panel chooses what the scene draws:

- **Triangle**: the clip-space diagnostic triangle above. The lifecycle UI tests use
  it, and it is the default.
- **Camera** (FF-06): the same triangle as model geometry, placed by an app-supplied
  `Transform` and viewed through a perspective `Camera` at (0, -0.5, 4.5). The pose
  buttons show one part of the transform each (Rest, Moved, Turned 60° about y,
  Scaled), and the slider sets the vertical field of view. In continuous mode the
  triangle also spins about its own y axis. Each change only rewrites the
  renderer's per-frame uniforms. The status text shows the pipelines and buffers the
  renderer created: 2 and 2, all in its initializer, so these numbers cannot change
  while drawing. The package tests check that drawing creates no GPU object.

- **Cube** (FF-07): the procedural cube as one indexed mesh, drawn by `MeshRenderer`
  with a depth buffer and back-face culling. Each face shows its model-space normal
  as a color: +x reddish, -x teal, +y light green, -y purple, +z lavender, -z olive.
  The pose buttons choose Front, Corner (-x, +y, and +z visible), or Stretched, and
  continuous mode spins the cube. The mesh is uploaded once when the scene loads;
  the status text shows 3 pipelines (the normal diagnostic plus the material
  fixture's two, all prepared on the same renderer at launch), 1 depth state, and 5
  buffers (two per-frame uniform buffers and the cube's position, normal, and index
  buffers) however long it animates. The view has a depth buffer only while a mesh
  fixture is shown.

- **Material** (FF-08): the cube's mesh, in the corner pose, shaded by a material
  instead of the normal diagnostic. **Unlit** is Frostfield's built-in unlit material;
  the Amber and Teal buttons change its color parameter. **Pulse** is
  `lab_pulse_fragment` from the app's own shader library (`LabShaders.metal`), with
  its parameter record declared once in `LabShaderTypes.h`, which Swift imports through
  the target's bridging-header setting. In continuous mode the app writes the
  animation time into the pulse material's parameters every frame and bands of color
  travel up the cube. Both materials are made when the scene loads, so the status text
  shows 3 pipelines (normal diagnostic, unlit, pulse) from launch, and they stay at 3
  while colors, materials, and time change. The material fixture shares the cube
  fixture's mesh, so the buffer count stays at 5.

Launch with `-FrostfieldLabFixture <triangle|camera|geometry|material>` to choose the
first fixture, `-FrostfieldLabCameraPose <rest|moved|turned|scaled>` for the camera
fixture's first pose, `-FrostfieldLabCubePose <front|corner|stretched>` for the
cube's, and `-FrostfieldLabMaterial <unlit|pulse>` for the material fixture's first
material.

The drawable size is set from the view's own bounds and
`traitCollection.displayScale` in `layoutSubviews`; nothing reads a screen-wide
value.

When the renderer cannot be created, the lab shows the typed `RendererError`
instead of a render view. Launch with `-FrostfieldLabSimulateMissingDevice` to see
that failure state on hardware that has a Metal device.

Launch with `-FrostfieldLabSimulateMissingDrawables <n>` to answer the renderer's
first `n` drawable requests with no target, as when `CAMetalLayer.nextDrawable()`
times out. With nothing in flight, the schedule asks for the owed frame once more:
with `1` the first frame is drawn on that retry, and with `2` the scene waits,
without further draw callbacks, until the next invalidation (for example Redraw).

## Experiments

[`Experiments/`](Experiments/) holds timeboxed backend spikes. They are not
Frostfield API and are not linked into the package or the lab app. The
[Metal 4 comparison](Experiments/Metal4Comparison/README.md) (FF-04) builds through the
two `Metal4*` schemes above; its targets sit in `FrostfieldLab.xcodeproj` and compile
sources from that folder.
The [Satin comparison](Experiments/SatinComparison/README.md) (FF-05) is an
isolated SwiftPM package with its own `Package.resolved`; it is not part of the
workspace and is built with `swift build` in its folder.

The executable work and acceptance gates are listed in [the backlog](../tasks/todo.md).
Simulator runs are integration smoke checks, not GPU or performance evidence.
